# 設計の方針 — なぜこの形にしたか

IT・SaaS業界への転職に向けたインプットを、毎朝ポッドキャストとして受け取るための設計メモ。
「どう情報を集めて、どう届けるか」の判断と、その理由を残しておく。

---

## 1. 前提：何のためのインプットか

転職のための情報収集は、業界全体を知ることが目的ではない。ゴールは 3 つに絞れる。

1. **面談で会話が成立する**　相手が前提として使う言葉が分かる
2. **志望動機に具体性が出る**　「業界が伸びているから」ではなく、特定の一本を語れる
3. **会社を自分で評価できる**　求人票とニュースを突き合わせて、事業の段階を読める

この 3 つから逆算すると、必要なのは網羅性ではない。
**語彙**と**論点**と**継続**の 3 つで、しかも続かないと意味がない。

だからこのアプリは、ニュースアプリではなく「毎朝 10 分の番組」という形にした。
情報の量を増やす道具ではなく、業界の言葉に毎日触れ続けるための仕組みとして作っている。

---

## 2. 情報収集をどう組むか

### 2.1 情報源は 3 層に分ける

1 種類の媒体だけを読むと、その媒体の編集方針がそのまま自分の世界観になる。
意図的に性格の違う 3 層を混ぜている。

| 層 | 役割 | 例 |
|---|---|---|
| 一次・速報 | 何が起きたかを最初に知る | ITmedia、CNET Japan、TechCrunch |
| 解説・分析 | なぜ重要かの視点をもらう | Publickey、SaaStr、a16z、Stratechery |
| コミュニティ | 現場の人が何に反応したか | はてなブックマーク、Hacker News、Zenn |

3 層目が効く。公式発表を読んでも「業界の人がそれをどう受け止めたか」は分からない。
面談で温度感がずれないのは、この層を毎日見ている人だ。

### 2.2 なぜ RSS を軸にしたか

選択肢は 3 つあった。

| 方式 | 利点 | 欠点 | 判断 |
|---|---|---|---|
| RSS / Atom | 無料、鍵不要、媒体側が整形済み、壊れても局所的 | 提供していない媒体がある、要約が短い | **採用** |
| ニュース API | 横断検索できる、整形済み | 有料、無料枠が厳しい、提供元に依存 | 見送り |
| スクレイピング | どこからでも取れる | 規約の問題、構造変更で壊れる、保守が重い | 見送り |

個人が毎朝使う道具に、課金と保守コストを持ち込みたくない。
RSS は「1 つ死んでも他は生きている」という壊れ方をするのが一番の利点で、
実際この設計では 1 媒体が落ちても番組は成立する。

ただし **フィードの URL は移転も停止もする**。これは避けられない。
そして実際に運用してみると、これが一番よく起きる故障だった。
開いても何も表示されない状態は、仕組みとしては動いているのに体験としては死んでいる。

そこで「正しい URL を最初から知っていること」に期待するのをやめた。
代わりに、壊れたときに自分で追いつく三段構えにしてある。

1. **代替 URL を順に試す**　媒体ごとに既知の別の場所を持たせておく
2. **サイト本体に聞きにいく**　全滅したらトップページを取り、
   `<link rel="alternate" type="application/rss+xml">` から移転先を読む。
   これは RSS の自動検出として昔からある仕組みで、移転したサイトはたいていここを直している
3. **手で直せる**　それでもだめなら画面から URL を入力できる。入力値はカタログより優先される

ヘルスチェックは ok / ng を返すだけでは足りない。
実際に読めた URL、移転していたかどうか、試して落ちた URL とその理由まで返して、
画面に「この URL に切り替える」ボタンを出せるようにした。
直し方が分からない故障は、直らない故障と同じだからだ。

### 2.3 増やしすぎない

情報源は足すほど良さそうに見えるが、実際は逆になる。

- 取得に時間がかかり、朝の待ち時間が伸びる
- 似たニュースが増えて、選別の質が落ちる
- 「全部は追えない」という感覚が生まれて、続かなくなる

なので既定では 9 媒体だけを ON にしてある。物足りなくなってから足す順番が正しい。

## 3. 集めた後に何をするか

集めるところまでは誰でもできる。価値が出るのは、その後の 4 工程にある。

### 3.1 重複をまとめる

同じニュースを 3 媒体で 3 回聞かされるのが、この手の仕組みで一番つらい。
一方で、機械的にまとめると別のニュースを潰してしまう。実際に難しいのは次の 2 つを同時に満たすことだ。

```
まとめたい：「SmartHRがシリーズEで150億円を調達」
          「SmartHR、150億円の資金調達を発表」        ← 言い回しが全然違う

分けたい　：「メルカリ、2025年度決算を発表」
          「ラクマ、2025年度決算を発表」              ← 社名以外が完全一致
```

文字の一致率（2-gram の Dice 係数）だけでは、後者のほうが高い数値になる。
そこで方向の違う手がかりを 3 つ重ねている。

1. **固有名詞**（大文字を含むラテン語と 3 文字以上のカタカナ）が両方にあって一つも重ならなければ、別の話題と断定する
2. 文字の一致率が十分高ければ同じ話題とみなす
3. 固有名詞と**数字**（年号を除く）を共有していれば、言い回しが違っても同じ出来事とみなす

年号を数字の手がかりから外しているのは、「AWSが2025年の決算を発表」と
「AWSが2025年に新サービスを投入」を誤ってまとめないため。
この判定は `server/__tests__/pipeline.test.mjs` に 15 組の実例として固定してある。

まとめた相手は捨てずに残す。**複数の媒体が同時に扱った = 重要**という強いシグナルになるからだ。

### 3.2 並べ替える

```
スコア = 鮮度 × 情報源の信頼度 × (1 + 興味の重み / 4) × (1 + 0.3 × 他媒体での言及数)
```

- **鮮度**は半減期 16 時間の指数減衰。朝聞くものなので、昨日の夜のニュースが一番強い
- **興味の重み**は 16 トピックごとに自分で調整できる。狙う領域を上げると、毎朝の内容が自分ごとに寄る
- タグが 1 つも当たらない記事も切り捨てない。辞書の外側にこそ知らない話題がある

### 3.3 偏らせない

スコア順に上から取ると、その日たまたま調子のいい 1 媒体で深掘りが埋まる。
**深掘りは 1 媒体につき 1 本まで**という制約を入れている。
選別の質を少し落としてでも、視野の広さを優先している。

### 3.4 昨日と同じ話をしない

過去に番組で扱った記事の URL を端末に持っていて、翌朝の候補から外す。
続報が出たときだけ「既出も含めて作り直す」で拾える。

## 4. なぜ「聞く」形にしたか

読む形式（メールやダッシュボード）にしなかった理由は 1 つで、**続かないから**。

朝の可処分時間で「座って読む」は競合が多すぎる。
一方、通勤・支度・移動の時間は耳が空いていて、ここには競合が少ない。
続けることが最大の要件である以上、耳を取りにいくのが合理的だと判断した。

### 番組構成

| コーナー | 尺の目安 | 狙い |
|---|---|---|
| オープニング | 30 秒 | 今日の全体像。聞くかどうかをここで決められるように |
| 深掘り × 3 | 各 2 分 | 何が起きたか → なぜ重要か → 自分にどう関係するか |
| 今日の用語 | 1 分 | 語彙を確実に増やす。ここが他のニュース要約との最大の違い |
| 転職メモ | 30 秒 | 今日から試せる具体的な一手 |
| 早耳ラウンドアップ | 1 分 | 見出しだけ。深追いしない割り切り |
| クロージング | 20 秒 | 「全部覚えなくていい」で終える |

深掘りの 3 段構成が肝になっている。
「何が起きたか」だけなら見出しで足りる。業界の外にいる人に必要なのは、
**それが業界の中でどういう意味を持つか**という 2 段目と 3 段目のほうだ。

## 5. 転職に効かせるための仕掛け

ここが、この仕組みを単なるニュース要約と分けている部分。

### 5.1 用語コーナー

業界の外からニュースを聞くと、内容よりも先に**知らない単語**で詰まる。
詰まった単語をその場で回収できないと、毎朝聞いても語彙が増えない。

42 語の辞書を持たせて、その日の記事に出てきた語を自動で拾う。
記事から拾えなかった日も、まだ扱っていない易しい語で必ず 1 つは埋める。
**語彙が増えない日をゼロにする**のが狙い。

各項目は 2 つの側面を持つ。

- **定義**：前提知識なしで 1〜2 文
- **面接での使いどころ**：その語をどう使うと話が通じるか

後者があることで、知識が会話に変換される。
「ARR とは年間経常収益です」で止まらず、
「御社は今 ARR どのくらいのフェーズですか、と聞ける」まで持っていく。

### 5.2 覚えた管理

覚えた語に印をつけると、以降は選ばれなくなる。
同じ語を何度も聞かされる無駄が消えて、辞書を前から順に踏破していける。

### 5.3 トピックの重み

「バーティカル SaaS の営業を狙う」のように的が決まっているなら、
SaaS とビジネスモデルの重みを上げておく。毎朝の内容が志望領域に寄っていく。

## 6. 割り切ったこと

正直に書いておく。

| 制約 | 内容 | なぜ許容したか |
|---|---|---|
| 画面ロック中は止まる | ブラウザの音声合成は、画面を消すと読み上げが止まる | 「画面を消さない」設定で凌げる。根本的には音声ファイル化で解決する |
| 要約が薄い日がある | フィードに含まれる要約が短い媒体がある | 記事本文の取得は各媒体の規約に関わるため踏み込まない |
| 端末をまたげない | 設定と履歴はブラウザの中だけ | 個人の関心そのものなので、手元から出したくない。書き出し／読み込みで代替 |
| フィードは壊れる | URL の移転・停止は起きる | ヘルスチェックで「どれが壊れたか」が即分かるようにした |
| 英語の読み上げ | テンプレート生成では英語見出しが英語のまま読まれる | Claude 経路では日本語化される。英語記事を扱うなら Claude を使う理由になる |

**画面ロックの制約が一番効いていた。** 通勤中にポケットに入れて聞く、という
本来いちばん使いたい場面が成立しなかった。これが音声ファイル化に踏み込んだ理由で、
音声合成を設定すれば、普段のポッドキャストアプリ側でこの問題は消える。

## 7. これからどうするか

### フェーズ 2：本物の音声にする（実装済み）

ブラウザ読み上げには 2 つの弱点がある。画面を消すと止まる端末があることと、
音声を持ち出せないことだ。これを解くには音声ファイルにするしかない。

実装した経路はこうなっている。

```
台本 → 音声合成 → ファイルとして保存 → ポッドキャストRSSで配信
```

音声合成は環境変数で選ぶ。VOICEVOX は自分で立てる代わりに鍵が要らず、
Google Cloud TTS は従量課金の代わりに立ち上げが不要。どちらも未設定ならこの経路は動かず、
アプリはブラウザ読み上げのまま使える。**設定していない人の体験を壊さない**ことを条件にした。

配信は普通のポッドキャスト RSS にした。独自アプリを作らないのが要点で、
ロック画面、バックグラウンド再生、オフライン、再生位置の記憶、倍速、スリープタイマーは
すべて既存のポッドキャストアプリが持っている。自前で作れば全部劣化版になる。

技術的に外せなかったのは範囲リクエスト（HTTP Range）への対応だった。
ポッドキャストアプリは途中から再生するために部分取得を投げてくる。
ここに 200 で全部返すと、シークも再生位置の復元も壊れる。

保存先はファイルシステムにした。自宅サーバーや VPS、Docker で動かす前提で、
これは VOICEVOX を動かす環境とも重なる。Vercel のような使い捨てのファイルシステムでは
残らないので、その場合は永続ディスクか外部ストレージに差し替える必要がある
（読み書きする関数は 4 つだけにしてある）。

#### 毎朝の生成を、サーバーの中に入れた理由

「毎朝 5 時に新しい番組ができている」を成立させるには、決まった時刻に走る仕組みが要る。
選択肢は外部の cron か、サーバー自身に持たせるかの 2 つだった。内蔵を選んだ理由は 3 つある。

1. **仕組みが 1 か所にまとまる**。cron を別に設定すると、アプリは動いているのに
   番組だけ増えない、という切り分けの面倒な故障が起きる
2. **時計のズレを自分で吸収できる**。サーバーの時計は UTC のことが多い。
   cron に `30 4 * * *` と書くと、日本時間の昼過ぎに走ることになる。
   内蔵なら「日本時間の 4:30」という指定をそのまま扱える
3. **取りこぼしを拾える**。ノートPCのように止まる機械では、予定時刻に走れないことがある。
   起動時に「今日の番組がまだ無い」と分かれば、その場で作ればいい。
   外部の cron には、この判断ができない

生成開始を 5:00 ではなく 4:30 にしているのも同じ発想で、
5 時に「これから作ります」と待たされるのでは、インプットの時間が削れてしまう。

### フェーズ 2.5：ブラウザのままでも、できるだけ近づける（実装済み）

音声合成を設定しない人にも、スマホで聞ける状態を用意した。

- **ロック画面とイヤホンのボタンから操作できる**。ただし読み上げは OS から
  「音声再生」と見なされないため、無音に近い音声をループ再生してメディア扱いにしている
- **再生中は画面を消さない**設定。iOS は画面が消えると読み上げが止まり、
  これは回避策がないので、現実的にはこれで凌ぐ
- **ホーム画面に追加できる**。圏外でも過去の番組を開ける

正直なところ、これは回避策の積み重ねであって、根本解決ではない。
毎日きちんと運用したいなら音声ファイル化のほうを勧める。

### フェーズ 3：聞くだけで終わらせない（未着手）

- **週次の振り返り**　その週に出た用語と主要ニュースを日曜にまとめて復習する
- **企業ウォッチリスト**　気になる会社を登録して、その会社のニュースだけ確実に拾う。面接前の下調べがそのまま貯まる
- **面接前ブリーフィング**　会社名を入れると、直近のニュース・使われている技術・想定質問をまとめて返す
- **書き出し**　覚えた用語を Anki などの暗記アプリ形式で出す
- **原文チャレンジ**　英語の一次情報を 1 日 1 本だけ原文で聞く。業界の一次情報は英語が先に出るので、慣れておく価値がある

### フェーズ 4：関心の学習（未着手）

今は興味の重みを手で調整している。
「最後まで聞いた」「記事を開いた」「用語を覚えた」といった行動を材料にして、
重みを自動で寄せていける。ただし**寄せすぎると視野が狭まる**ので、
一定割合は意図的に興味の外側を混ぜる余地を残しておきたい。

---

## 8. 一言でいうと

集めることではなく、**毎朝続くこと**と**語彙が増えること**に寄せて設計した。

情報収集の仕組みを作ると、つい網羅性を上げたくなる。
でも転職のインプットで効くのは、広さではなく「業界の言葉で考える時間が毎日あること」のほうだ。
10 分の番組という枠を先に決めて、そこに収まる量だけを選ぶ設計にしているのは、そのため。
